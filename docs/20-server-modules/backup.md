# backup — зашифрованные резервные копии узлов

**Роли:** entry, exit, solo.

## Зачем
Без копии смерть сервера, к которому подключаются клиенты, означает перевыдачу профилей всем. Теряется:
- `users.json` (клиенты подписки и Telegram-прокси) и ключи AWG;
- секреты MTProxy;
- сертификаты.

## Как устроено
- **`/usr/local/sbin/vpnkit-backup.sh`** по таймеру `vpnkit-backup.timer`: выход в 04:00, вход в 04:30, ±10 мин, `Persistent=true`.
- **Шифрование — [age](https://age-encryption.org) на открытый ключ пульта** (`/etc/vpnkit/backup.recipients`, берётся из `vpnkit secrets pubkey`).
  - Узел копию создаёт, но расшифровать её не может.
  - Открытый текст на диск не пишется: `tar | age`.
- **Базы SQLite** (параметр `sqlite`) копируются через backup API SQLite, а не простым tar: живые базы с WAL иначе бывают битыми.
- **Что копируется** — список `PATHS` в `/etc/vpnkit/backup.conf`. Файлы, не управляемые vpnkit, не копируются.
- **Хранение:**
  - 7 своих копий в `/var/backups/vpnkit/` (600);
  - главная копия — на компьютере пользователя: `vpnkit backup pull` или кнопка «Забрать свежую копию».

## Пульт
```
vpnkit backup pull all                  # свежие копии в ~/.vpnkit/backups/<узел>/, sha256 сверен, содержимое проверено
vpnkit backup verify <файл>              # расшифровать ключом пульта и проверить ключевые файлы
vpnkit backup extract <файл> <каталог>   # распаковать для восстановления (там секреты — удалить после)
```
Ключ пульта — `~/.vpnkit/age.key`. **Без него копии не расшифровать.** Храните его копию отдельно от ПК: менеджер паролей или офлайн-носитель.

## Ловушки, пойманные при запуске
- `grep -v` без совпадений возвращает 1, а с `pipefail` это ронял скрипт.
- tar возвращает 1 на «файл изменился во время чтения», хотя архив при этом цел. Разрешено, ошибкой считается только код больше 1.
- Шаблоны исключений (`*__pycache__*`) нельзя раскрывать оболочкой (`set -f`).
- Без `umask 077` недописанные файлы появлялись с правами 644.

## Восстановление (эскиз, отработать на тестовом сервере)
1. Поставить base-host и amneziawg.
2. `vpnkit backup extract` на ПК.
3. Положить файлы на новый сервер по тем же путям.
4. Сделать `systemctl daemon-reload` и включить службы из `etc/systemd/system`.
5. Базы из `sqlite/` вернуть на место.
6. Выпустить сертификаты заново, если сменился IP или DNS.

## Модуль установщика

`vpnkit install <узел> backup` ставит модуль на новом узле без ручных шагов:

- скрипт `vpnkit-backup.sh` едет с пульта (`agent/backup/files/`) и ставится в `/usr/local/sbin`;
- получатель шифра — открытый ключ пульта из `~/.vpnkit/age.key`. Без ключа модуль не ставится и подсказывает `vpnkit secrets init --key`;
- в `backup.conf` попадает всё, чем управляет vpnkit. Чего на узле нет, скрипт пропускает. Дописать своё можно параметром `extra_paths`, базы SQLite — параметром `sqlite`;
- время: exit в 04:00, остальные в 04:30, плюс случайный сдвиг до 10 минут. Параметр `time` меняет время;
- Шаг verify требует, чтобы последняя копия была моложе часа, sha256 сходился, права были 600, а заголовок был age. Расшифровать её узел не может.
- `vpnkit backup verify` проверяет копию по меткам модулей `var/lib/vpnkit/modules/*` внутри неё: у каждого модуля свой список обязательных файлов (`internal/backup` → `ByModule`). Если в копии меток нет, это не копия узла vpnkit — проверка так и скажет.

На тестовых серверах: копии сделаны, забраны пультом, расшифрованы, файлы всех модулей на месте.

## Восстановление клиентов

Сервер заменён или его данные потеряны. Клиентам ничего перевыдавать не нужно:

- **AmneziaWG:** `vpnkit clients resync <узел>`. Ключи и адреса клиентов лежат в хранилище пульта (профили), из них пиры возвращаются на вход без перезапуска. Пиры на узле, которых нет в хранилище, не трогаются, только перечисляются.
- **Подписка и Telegram:** `vpnkit restore clients <узел> <копия.tar.gz.age>`. Реестр `/etc/vpnkit/users.json` (UUID, токены подписок, пароли hysteria2, ключ VLESS Encryption, секреты MTProxy) достаётся из зашифрованной копии.
  - Узел проверяет, что это реестр (schema 2), и сохраняет текущий в `clients-backup`.
  - Затем пересобирает xray, sing-box, telemt и подписки.
  - В конце каждая подписка проверяется через 443: должна ответить 200.

Порядок на новом сервере: `bootstrap` → модули (`deploy`) → `restore clients` → `clients resync`.

**Проверено на тестовых серверах.**
- AWG: пир удалён из конфига и интерфейса, после `resync` он вернулся, конфиг совпал с тем, что был до потери.
- Реестр: подписка и Telegram-клиент удалены, ссылки перестали работать (подписка 404, hysteria2 «authentication failed», MTProto отвечает маской). После `restore clients` все три входа и MTProto снова работают с прежними ключами.

**Ограничение.** Профили AWG содержат адрес сервера. При замене сервера с новым IP клиенты AWG перенастраиваются: им нужна новая ссылка из той же карточки, ключи остаются прежними. Подписка и Telegram ходят по именам, поэтому после переноса DNS-записи на новый IP продолжают работать сами.
